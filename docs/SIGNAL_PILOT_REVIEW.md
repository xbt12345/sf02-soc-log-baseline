# 消息信号原型：真实日志试验复核

日期：2026-09-11。结论：**本地与用户回传的云端真实日志流程均已执行，当前检测原型不合格；没有证据证明可迁移。** 下文区分本地实测、用户回传和待核对事项。

后续更新：用户已回传两端内容核对全部通过，v2 也已在本地实现并执行。本文保留 v1 的结果和当时的修改依据；当前决策以 [BEHAVIOR_V2_REVIEW.md](BEHAVIOR_V2_REVIEW.md) 为准。

## 云端回传与本轮新增诊断

用户已回传完整 v1.1 结果：100,000 行抽样、8,763 行评价、84 棵树，耗时 223.404 秒，进程峰值 RSS 1,228,709,888 字节（1.1443 GiB）。该值不代表整个容器占用。云端 Macro-F1 与本地只差约 1.11×10^-16，恶意召回、无信号比例等摘要指标一致。原始回传见 [signal_pilot_cloud_user.json](../platform/signal_pilot_cloud_user.json)，对照记录见 [signal_pilot_cloud_comparison.json](../platform/signal_pilot_cloud_comparison.json)。

源码 SHA-256 与冻结 v1.1 相同；该源码在训练前强制核对两份官方输入哈希，因此这份成功回传支持哈希检查已通过。助手未独立读取云端原件。配置、切分 Parquet、模型的字节哈希不同；配置路径/线程、Parquet 编码与元数据、模型运行信息均可能影响字节，不能凭摘要认定具体原因。随后用户回传 [只读内容核对全部通过](../platform/pilot_content_verification_cloud_user.json)：两端清单内容、逐行预测类别一致，正常/恶意/可疑召回分别为 1、0.746365、0。完整概率数组未比较，原始输入在此次只读复核中没有重新计算哈希；具体字节差异原因未定位。

随后只使用冻结的训练/开发区做了特征诊断，没有重训，也没有用校准/评价区选新规则。实际重建了 65,062 条记录的特征，并逐条核对原始行号、event_id 和消息组与清单一致。根因比“覆盖不足”更明确：**训练区 56,536 条日志只有 6 种不同的特征向量，23 个预设特征只有 5 个曾非零。**

|---|---:|---:|---:|
| 全部信号为零 | 42,744 | 1,137 | 270 |
| 认证失败 | 71 | 0 | 9 |

全部 1,801 条可疑样本都与别的类别共享同一输入，而且没有一个向量组以可疑为多数。冻结模型在训练区也一次没有预测可疑。这直接解释了上一版在无权重、默认 argmax 下的可疑类塌缩：提取过程丢失了可区分信息。改权重能改变整组的预测和误报/漏报取舍，但无法恢复同一向量内部的逐条差异。这不证明原始日志不可识别，也不证明全量数据上的统计关系一定相同。

### 对第二版的具体调整

1. **先抽结构，再统一行为。** 当前认证规则漏掉了原文 `An account failed to log on`、Duo 的 `auth_failure`/`result`，网络规则漏掉了 VPC 的 `REJECT OK`。这些都是训练区已存在的证据，应先用格式明确的解析器保留动作、结果、原因和适用的协议/请求字段。Windows 4625 表示登录失败，仍需上下文判断威胁，不作为恶意标签表。[Microsoft 官方说明](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4625)
2. **区分业务动作与日志状态。** VPC 的 REJECT 表示流量被拒绝，OK 表示日志正常记录；不能把 OK 解读为事件安全，也不能把 REJECT 解读为攻击已证实。[AWS 字段定义](https://docs.aws.amazon.com/vpc/latest/userguide/flow-log-records.html) Duo 的无响应、口令无效和明确欺诈不是同一含义，应保留原因，不能只合并为 denied。[Duo 认证日志定义](https://duo.com/docs/adminapi#authentication-logs)
3. **先补规范化缺口，再试文本模型。** v1.1 指定格式的扰动检查通过不等于所有日期/身份都被移除。训练样例仍保留 syslog 月份、部分 Unix 秒数和损坏的脱敏片段，包装前缀/转义文本也未完整拆解。不能直接把现有 normalize 输出交给自由 n-gram 模型，避免重新引入时间、实体和来源捷径。
4. **给新表示设置进入训练的条件。** 保存实际命中片段和每类/来源覆盖；比较特征碰撞、同源不同标签、正常拒绝与攻击放行的支持量；测试表示等价、批次一致、否定/布尔 false 和损坏字段。信号更多并不自动意味着更可靠。新分组若合并了旧清单的跨区消息，必须报告并处理跨区连通，不能静默保留泄漏划分。
5. **先补可比证据，再评价迁移。** 拒绝访问向量里，当前抽样的恶意来自产品字段缺失组，可疑主要来自 ASA；不能通过重新放入产品/缺失字段解决这次塌缩。以来源留出暴露缺失支持，再补同源正常/攻击对照。对确认已不可比的来源，报告 N/A 而不是随机混分。

以上记录 v2 实施前的诊断依据。后续已完成有限的第二版解析和来源留出，详见 [v2 实测复核](BEHAVIOR_V2_REVIEW.md)；没有借用旧评价区标签拟合、校准、早停或评分。

## 固定试验与结果

v1.1 单文件入口：[soc_signal_pilot.py](../training/soc_signal_pilot.py)。两份本地官方输入 SHA-256 均匹配。从全部 2,056,871 行训练数据中均匀抽取 100,000 行，种子固定 20260911；23 个固定词法动作信号，按规范化消息组隔离训练、开发、校准、评价。没有读取官方验证答案，也没有使用官方验证输入调参。

最大消息组有 17,297 行，所以按组 70/10/10/10 分配不会形成同样的行数比例。实际切分如下，没有为修饰分布拆组或换种子：

| 用途 | 正常 | 恶意 | 可疑 | 消息组 |
|---|---:|---:|---:|---:|
| 训练 | 50,900 | 3,835 | 1,801 | 14,350 |
| 开发 | 7,655 | 721 | 150 | 2,095 |
| 校准 | 25,810 | 314 | 51 | 2,086 |
| 评价 | 7,910 | 619 | 234 | 2,075 |

一次无权重 CatBoost，最多 200 棵深度 5 的树，开发区提前停止，实际保留 84 棵；本地使用 CPU 4 线程。v1.1 完整运行约 95.1 秒，多数时间在读取与文本抽取。Windows 未配置进程内存监控，因此峰值内存为 N/A，不能据此估算云端峰值。

| 评价项 | 实测 |
|---|---:|
| Accuracy | 95.54% |
| Macro-F1 | 0.59536 |
| 同一评价区全判正常 Macro-F1 | 0.31628 |
| 恶意 Precision / Recall | 87.67% / 74.64% |
| 可疑 Precision / Recall | 0 / 0 |
| 三分类 argmax 的正常误报 | 0 / 7,910 |
| 样本中没有动作信号的比例 | 82.448% |

三类混淆矩阵按“正常、恶意、可疑”排列，行是真值，列是预测：

```text
[[7910,   0, 0],
 [ 157, 462, 0],
 [ 169,  65, 0]]
```

这意味着模型一次也没有预测可疑类，234 条可疑全部误判。可疑类在抽样中已有 1,712 / 2,236 条命中至少一个信号，所以问题不只是“有没有关键词”，还包括信号能否区分相同动作的不同安全含义。

模型对 `access_denied` 的 CatBoost 特征重要性约 87.57%。这只说明模型高度依赖该信号，不能证明“拒绝访问就是攻击”。裸产品字段虽然没有进入模型，来源格式和常用措辞仍可能通过消息信号间接进入；来源留出必须继续做。

## 零误报与低阈值报警需要分别解释

上面的 0 次正常误报来自三分类 argmax。报警预算试验另使用 `1 − P(benign)`，只根据校准区正常样本选择阈值：

- 设定校准误报预算为 0.1%，即每万正常最多约 10 次。
- 实际选出的阈值约 0.0320646052，校准区正常误报 2 / 25,810。
- 应用到固定评价区后，正常误报变为 17 / 7,910，即 **每万正常约 21.49 次**，超过 10 次预算。
- 此报警阈值的恶意检出率为 74.64%，可疑检出率为 27.78%；这表示被报为非正常，并非正确完成了三分类。

该原型输出分数较离散，三个预算点选出了相同阈值，不能把它画成精细、连续、可任意控制的报警曲线。也没有对概率进行校准。

组 bootstrap 的 Macro-F1 描述性 95% 区间约 `[0.536, 0.634]`，恶意召回区间约 `[0.519, 0.873]`，已经显示按组看不确定性明显。三分类观察到零正常误报时，普通 bootstrap 只会不断重复零；v1.1 明确将相应区间置空并说明原因，**不输出 `[0,0]` 暗示风险不存在**。即使采用独立样本的统计上界，也必须先有适用的独立性依据，当前没有。

## 真实数据问题与调整顺序

抽样中 172 条消息以 JSON 对象/数组形式开头，172 条均未通过标准 JSON 解析；这只描述该抽样范围，不代表全体日志都是 JSON，也不代表全体都损坏。已查看样例包含被脱敏标记替代的字段名、动作词和未加引号数值。原文不能可靠恢复的地方保留未知，不能用标签猜回字段，也不能将“解析失败”当作攻击证据。

以下保留 v1 诊断时的推进顺序；部分已由 v2 执行，当前优先级以 v2 复核为准：

1. **改进可审查的字段抽取。** 在训练/开发区先按格式核对 syslog、CEF、XML、受损 JSON 的动作、结果、请求和进程证据。每个字段保留命中片段、未知状态及抽取覆盖，优先解决同动作正常/攻击混淆。规则可能是弱证据，不把厂商严重性或告警名称当真值。
2. **检查表示是否足够区分标签。** 统计相同特征向量与相同消息组的标签冲突；对缺乏上下文的行明确不可识别。可疑类需要依据官方标签含义识别，不等同于“置信度低”，也不能靠极端权重掩盖特征不足。
3. **补来源留出和必要数据对照。** 核对同产品、同时间/采集条件下的正常拒绝、合法管理、攻击放行等。某来源缺少某类时报告支持不足，不构造虚假的齐全测试。确认外部规则后准备独立环境评价，避免用已见官方验证集反复筛选模型。
4. **再比较权重与文本支线。** 在覆盖和评价可信后比较温和权重、受控文本模型及必要融合。以固定误报成本和分来源表现决定是否采用，而非总准确率。

当前官方训练集足够发现这些问题并继续开发；**不足以证明换环境后仍然可靠**。先补同语义、不同环境/类别的真实对照与独立评价数据，再按明确缺口补训练数据，比单纯增加相同模板的数量更有价值。

本次内部评价区已经查看，后续依据这些错误修改的模型不能再把它称为未见测试。保留它作诊断；最终迁移结论仍需提前冻结的新来源/新环境。
